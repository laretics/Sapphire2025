Lenguaje de planificación de demanda Diamond mini-DSL

Referencia del mini-lenguaje que describe qué servicio se desea (origen, destino, cadencia, paradas y días). El planificador de Diamond lo convierte en una malla horaria de circulaciones con asimilaciones cinemáticas, numeración SFM y detección de conflictos de cantón.

1. Introducción

El script de demanda es texto plano, codificado en UTF-8, con una instrucción por línea. Los comentarios empiezan por #. Las líneas en blanco se ignoran. Las líneas indentadas (espacio o tabulador al inicio) son continuaciones del último require.

El lenguaje es determinista: el mismo script y la misma topología producen la misma malla (mismo orden de requisitos, mismas salidas y mismos números de tren).

2. Flujo de trabajo

  1. Script de demanda — mini-DSL con include del XML de topología + plan + require…
  2. Compilación — DemandScriptParser + carga del topo vía TopoStorage + resolución de estaciones.
  3. Planificación — MeshPlanner.Solve(día) genera circulaciones y asimilaciones.
  4. Numeración — series SFM por corredor OD (impares ↑PK, pares ↓PK).
  5. Visualización — malla tiempo × PK; conflictos en rojo.

En la UI de demo (/mesh) puedes editar el script, filtrar por día, importar rauta → script y elegir la View (eje o camino multi-eje).

3. Gramática resumida

plan "nombre del plan"
train default "Modelo" accel 0.9 brake 0.8 vmax 160

days lab
  color #38bdf8
    require|req [both [ways]] [<frecuencia>] <origen> -> <destino>
            [ventana] [using flota] [as id]
      stops 30s
      skip RLL Enllaç "Sant Joan"
      dwell INC 1min
      cross at Petra
ElementoDescripción
includeDeclara la topología Diamond a cargar (TopoStorage). Basta el nombre; se asume .xml. Alias: incluir.
planNombre opcional del plan (metadato).
train / trenTipo de material (TrainSpecs): id, nombre, accel, brake, vmax. Si no hay ninguno, se usa el modelo por defecto.

4. include — topología

include toposfm227
include topo "Samples/Onice/toposfm227"
incluir "C:/datos/mi-red.xml"

Declara el almacén de topología (TopoStorage) del plan: un fichero XML Diamond (formato canónico o legacy Onice) con ejes, estaciones y vías. Al compilar (Plan.CompileDemand), se carga el layout y se usa para resolver estaciones y restricciones de sesión. No hace falta inyectar el topo desde fuera.

  • Solo se admite un include de topología por script (nivel raíz, sin indentar).
  • La extensión es siempre .xml: con solo el nombre (include toposfm227) se asume toposfm227.xml. Si la ruta ya termina en .xml, no se duplica.
  • Rutas relativas se resuelven con Plan.ScriptBaseDirectory (si está vacío, el cwd).
  • Formas: include nombre, include "ruta", include topo …, incluir ….
  • Sigue siendo válido asignar Plan.Topo a mano (tests, host) si no hay include.

5. plan

plan "SFM T3 laborables"

Asigna el nombre del plan al resultado de compilación. No afecta a la malla. Si se omite, el plan puede quedar sin nombre o con el que asigne la aplicación.

6. train / tren — material rodante

train default "Modelo" accel 0.9 brake 0.8 vmax 160
train s3300 "Civia S-3300" accel 0.85 brake 0.75 vmax 120
tren metro
  name "UT Metro"
  accel 1.0 m/s2
  brake 0.9
  vmax 100 km/h

Define un Diamond.Motion.TrainSpecs en el catálogo del plan (cabecera del script). Los require … using id referencian este id.

CampoSintaxisUnidad / defecto
Idprimer token tras trainobligatorio, estable
Nombreliteral o name "…"por defecto = id
Aceleraciónaccel / am/s² (defecto 0.9)
Freno serviciobrake / freno / bm/s² (defecto 0.8)
Vmax materialvmax / vkm/h (defecto 160)
  • Nivel raíz (sin indentar). Alias: tren, fleet.
  • Propiedades omitidas heredan los del modelo por defecto (TrainSpecs.DefaultModel).
  • Si el script no declara ningún train, al compilar se genera automáticamente el tipo default.
  • Si declara al menos uno, el catálogo del plan se sustituye por el del script (fuente de verdad).

7. require / req

Forma general (req es sinónimo de require):

require|req [both [ways]] <freq> <from> -> <to> [ventana] [using id] [as id]

Sentido

SintaxisSignificado
require … A -> B Solo un sentido: de A hacia B.
require both ways … A -> B Ida y vuelta. El motor planifica primero el sentido de PK creciente (números impares) y después el de PK decreciente (pares), ambos desde el inicio de la ventana.
require both … Equivalente a both ways (ways es opcional).

Identificador del requisito

require 2/h PMI -> MAN as R-T3

Con as ID fijas el id del requisito (aparece en errores y como DemandId de las circulaciones). Sin as, se asigna automáticamente R1, R2, …

FormaEjemploInterpretación

N/h2/hN trenes por hora (intervalo 60/N min).
N per hour4 per hourIgual que N/h.
every N minevery 40 minUn tren cada N minutos en cada sentido planificado.
 
# Un tren Palma→Manacor a las 06:05 (sin cadencia)
req PMI -> MAN 06:05-07:00 as R-4901
  days lab

# Ida y vuelta: un impar y un par
req both ways PMI -> SPB 05:35-06:30 as R-pair
Cuando hay frecuencia, la cadencia es un deseo. Si la infraestructura (cantones / vía única) no la permite, el planificador puede avisar y usar un intervalo mínimo estructural mayor, o planificar a la cadencia pedida y marcar conflictos.

7. Ventana horaria

Define el intervalo de salidas admitidas (hora del día).

FormaEjemploInterpretación
Compacta (rango)06:00-22:00Inicio y fin explícitos.
Compacta (una hora)5:35Equivalente a 5:35-6:35 (fin = inicio + 1 h).
Explícitafrom 06:00 to 22:00Misma idea, más verbosa.

Si se omite la ventana, el planificador usa por defecto aproximadamente 06:00–22:00. El fin debe ser posterior al inicio. Con una sola hora cercana a medianoche, el fin se limita a 23:59. 

req PMI -> SPB 5:35 as R-one
# igual que: req PMI -> SPB 5:35-6:35 as R-one

require every 40 min PMI -> MAN 06:05-22:20 as R-lab
require 1/h PMI -> SPB from 06:00 to 21:00

8. Estaciones (origen / destino / skip / dwell)

Las referencias de estación se resuelven contra el catálogo topográfico en este orden:

  1. Id exacto (p. ej. 01, 24)
  2. AVR exacto (p. ej. PMI, MAN, SPB)
  3. Nombre exacto (p. ej. Palma, Petra)
  4. Coincidencias sin distinguir mayúsculas (con desambiguación determinista si hay duplicados legacy)

Conviene usar AVR o id Onice para evitar ambigüedades (p. ej. Inca vs Pont d'Inca).

Códigos frecuentes SFM (demo):
PMI Palma · MAN Manacor · SPB Sa Pobla
INC Inca · UIB UIB · PET Petra · RLL Son Rullán

10. Flota — using

require every 15 min PMI -> UIB using metro as R-Metro

Selecciona el material / TrainSpecs del catálogo del plan (declarado con train: aceleración, frenado, Vmax). Si el id no existe, se avisa y se usa el modelo por defecto.

10. Días de servicio — days / on

Indica en qué días de la semana aplica el requisito. El planificador (Solve(DayOfWeek) solo materializa los requisitos del día elegido.

TokenSignificado
lab, laborables, weekday(s)Lunes–viernes
fes, festivos, weekend, weSábado–domingo (aprox. festivos)
all, todos, dailyTodos los días
lun…dom / mon…sunDía suelto
lun-vie, mon-friRango inclusivo
 
require both ways every 40 min PMI -> MAN 06:00-22:00 as R-T3
  days lab

require 1/h PMI -> MAN 07:00-21:00 as R-fes
  days fes

require 2/h PMI -> UIB
  days lun mie vie

Por defecto, si no se indica days, el requisito aplica a todos los días.

11. Patrón de paradas

Controla detenciones intermedias del perfil de marcha (asimilación). Origen y destino siempre arrancan/paran a v=0; las intermedias dependen del patrón.

stops <duración>

Activa el modo de patrón explícito: se consideran todas las estaciones del trayecto (no solo principales), con dwell por defecto. 

  stops 30s
  stops 1min

Duraciones: 30s, 30 sec, 1min, etc.

skip EST1 EST2 …

Estaciones del trayecto en las que no se para (pasante).

  skip RLL Enllaç "Sant Joan" PSJ

dwell ESTACIÓN <duración>

Sobrescribe el dwell en una estación concreta.

  dwell INC 1min
  dwell PET 2min
Sin stops ni overrides, el planificador usa un modo legacy: solo estaciones principales intermedias con dwell 0 (útil para prototipos).

12. Cruce — cross at

  cross at Petra
  cross at Enllaç

En requisitos both ways, intenta desfasar ida y vuelta para que se encuentren en la estación indicada (si está en la vista de ruta). Si no hay cross at, ambos sentidos arrancan al inicio de la ventana (fase 0); primero se planifican todos los impares y luego todos los pares.

13. Color de circulación — color / colour

Asigna un color de traza a todas las circulaciones generadas por el requisito. Si se omite, el SVG usa la paleta por asimilación (mismo perfil de marcha → mismo color).

FormaEjemploResultado
#rrggbbcolor #e11d48Hex de 6 dígitos.
#rgbcolor #f00Se expande a #ff0000.
Sin almohadillacolor aa00aaEquivalente a #aa00aa.
Nombre CSScolor orangeNombres básicos (red, blue, teal…).
Inlinereq PMI -> MAN 06:00-08:00 color #38bdf8También en la misma línea del require.
 
req both ways every 40 min PMI -> MAN 06:00-22:00 as R-T3
  days lab
  color #f472b6

# Sin color → color automático por asimilación

Los literales #rrggbb no se confunden con comentarios: un # seguido de 3/6/8 dígitos hex es color; el resto de usos de # siguen siendo comentario de línea.

14. Regiones de definición

Una región es un bloque indentado que fija valores por defecto (days, color, …) para todos los require que contiene. Las regiones se anidan: el hijo redefine o añade propiedades; al salir del indentado, el ámbito se cierra.

FormaEjemplo
Propiedad soladays lab / color #f00
Varias en una líneadays lab color #e11d48
Con palabra clavewith days lab color #e11d48, con …, region …
 
days lab
  color #f472b6
    req both ways every 40 min PMI -> MAN 06:00-22:00 as R-T3
      stops 30s
      cross at Petra
    req both ways every 60 min PMI -> SPB 06:00-21:00 as R-SPB
  # solo hereda days lab (fuera del color)
  req PMI -> UIB 07:00-20:00 as R-metro

with days fes color #38bdf8
  req PMI -> MAN 08:00-20:00 as R-fes
Prioridad: valor en el propio require (inline o continuación indentada) > región más interna > regiones externas > defecto del lenguaje (days = todos los días, sin color de script). Las continuaciones stops/skip/dwell/cross siguen siendo solo del require, no abren región.
Distinción importante: si color/days van más indentados que un require, aplican solo a ese require (continuación). Si van al mismo nivel que otros requires anidados (o en una línea de región), abren ámbito para lo que cuelga debajo.

15. Borrado de franja — delete / del

Directiva de post-proceso ordenado: se aplica sobre las circulaciones ya planificadas por los require anteriores en el script. Los require posteriores se planifican después (ideal para trenes especiales en un hueco, y base de futuros include).

SintaxisEfecto
delete 12:00-14:00 Elimina circulaciones cuya salida cae en [12:00, 14:00).
delete 12:00-14:00 all Además elimina las cuyo trayecto solapa la franja (aunque salgan antes o lleguen después).
delete from 12:00 to 14:00 all Forma explícita equivalente.
del … Alias corto de delete. 
days lab
  # Malla base cada 40 min
  req both ways every 40 min PMI -> MAN 06:00-22:00 as R-T3
    stops 30s
  # Hueco al mediodía (también trenes en ruta)
  delete 12:00-14:00 all
  # Tren especial en el hueco
  req PMI -> MAN 12:30-13:30 as R-special
    color #fbbf24
Hereda days de la región contenedora: un delete bajo days lab solo actúa al planificar laborables. El motor registra un warning con el recuento de circulaciones eliminadas.

16. Semántica del motor de malla

  1. Camino — se busca un camino de estaciones (un eje o multi-eje, p. ej. Palma–Enllaç–Sa Pobla = T3+T2).
  2. Asimilación — perfil cinemático a lo largo del PK de ruta (límites de velocidad del eje, paradas, aceleración/frenado del tren).
  3. Salidas — para cada sentido, desde el inicio de ventana, cada headway (deseado o estructural mínimo).
  4. Both ways — (1) todos los trenes del sentido ↑PK; (2) todos los del sentido ↓PK. No se intercalan por hora deseada.
  5. Conflictos — no se retrasan salidas para “buscar hueco”: se planifica a la cadencia y, si hay incompatibilidad, se registra error y se mantiene la circulación.
  6. Filtro por día — solo requisitos cuyo days incluye el día de Solve.

18. Conflictos y visualización

Un conflicto duro es la superposición de dos rectángulos de ocupación de cantón (tiempo × PK) cuando no está permitido (p. ej. cruce en vía única, dos trenes en el mismo cantón).

  • En la malla SVG, la intersección se pinta en rojo.
  • Un triángulo de aviso marca el centro del solape.
  • Los mensajes de error citan los números de tren implicados.
Sentidos opuestos en tramo de doble vía se consideran compatibles (no generan conflicto de cruce).

20. Importación desde rauta (compilador inverso)

Diamond puede inferir un borrador de script a partir de una malla rauta Onice + catálogo de asimilaciones del topo:

  • Agrupa bloques por OD y empareja ida/vuelta cuando es posible.
  • Estima cadencia (mediana de huecos) y ventana (primera–última salida).
  • Infiere stops / skip / dwell desde los trips Onice.
  • Servicios dispersos (p. ej. un solo 7001/7002) no se convierten en cadencia cada 60 min todo el día.
  • Los caminos multi-eje se anotan en comentarios (multi-eje T3:…+T2:…).
El script inverso es editable. Los tiempos cinemáticos de Diamond pueden diferir de las asimilaciones Onice; la malla resultante es una replanificación, no un clon 1:1 de las horas rauta.

21. Consejos prácticos

  • Usa AVR estables (PMI, MAN) en lugar de nombres largos.
  • Pon days lab / days fes en productos distintos; filtra el día en la UI.
  • Para multi-eje, elige la View correcta en la malla (p. ej. T3+T2 para Palma–SPB).
  • Si ves muchos rectángulos rojos, revisa cadencia y vía única; el motor no “empuja” trenes para evitar el choque.
  • Los ids as R-… ayudan a leer errores y numeración en depuración.
